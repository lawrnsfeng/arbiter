# A3 security and privacy
## Mission
Find security or privacy flaws the added code introduces, each traced from an attacker-controlled source to a dangerous sink with every hop cited.
## Axes
`security`, `privacy` (research-axes.md §2a axes 6–7; method from research-security.md §2).
## Read these language references
`security.md` (appended below).
## Checklist
1. Read the threat model in the inputs first. Its trusted inputs, in-scope and out-of-scope classes and DoS policy bind you (S36: 90% exploitable with one; 40% FP without).
2. Scope: only security impact this change adds (S35). A new caller, route or input that reaches an old sink counts.
3. For each candidate, trace source → transforms → sanitizer → sink. Cite `path:line` for every hop. Name the trust boundary crossed. A finding with a missing hop is not a finding.
4. Classes: injection (SQL 89, OS command 78/77, code 94, XSS 79), path traversal (22), deserialization (502), SSRF (918), missing authz or IDOR (862, 863, 639), missing authn (306, 287), mass assignment (915), secrets in code or logs (798, 532), PII in logs or responses (200, 359), LLM output reaching a sink (treat model output as a taint source).
5. Authz: for a handler that loads or changes a record by a client ID, look for the owner, tenant or role check in the handler, middleware and router. Read them.
6. Severity, answered before rating (S36 six questions): reachability, attacker control, preconditions, authentication, read vs write, blast radius. Unauthenticated remote with no preconditions → `block`. One or two preconditions or an authenticated path → `should-fix` unless the impact is severe. Local-only or three+ preconditions → `nit` or skip.
## Do not report
- Env vars and CLI flags as attacker input; UUID guessing; test files and docs; client-side authz checks.
- XSS in React/Angular output unless `dangerouslySetInnerHTML`, `bypassSecurityTrust*` or a raw DOM sink is used.
- SSRF unless the attacker controls the host or protocol. Logging URLs.
- DoS, ReDoS or resource exhaustion unless the threat model's DoS policy puts them in scope.
- Prompt injection unless the agent has tools, secrets or write scope.
- A SAST-style pattern match without a traced source. Placeholder or test credentials.
## Proof plan hints
- E4: an exploit-style test: the attacker input enters at the entry point and the test asserts the sink is not reached (e.g. the table still exists, the file outside the root is not read, the response is 403).
- E3: a snippet showing the built query, command or path contains the payload unescaped.
- E2 (SAST hit) is supporting only; never plan it alone.
