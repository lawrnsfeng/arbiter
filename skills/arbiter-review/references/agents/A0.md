# A0 intent
## Mission
List the behaviours this change claims to deliver, name their source and the threat model, and note the risk of each plan-required unit.
## Axes
None directly. Your output feeds SPEC (spec conformance) and A3 (security). Ranked first in research-axes.md §4: everything depends on understanding the change (S3).
## Read these language references
None.
## Checklist
1. Read the commit messages and PR text in the inputs. Each concrete promise ("adds X", "fixes Y", "no behaviour change") becomes one item in `claims`. Write claims as checkable statements, not as praise.
2. Look for a spec: issue refs (`#123`, `Fixes …`) quoted in the inputs, and files under `specs/`, `docs/`, `design/`, `rfcs/` that the commits or the changed files name. Use glob and grep to find them; read them. Add each acceptance criterion as a claim.
3. Never trust the claims. Agents trust misleading PR descriptions (research-axes.md §2a axis 11, S9). You only list them; SPEC checks them.
4. `spec_source`: the path or issue ref you used, else `none`.
5. Threat model: if the inputs contain one, or `THREAT_MODEL.md` / `docs/THREAT_MODEL.md` exists (glob for it), set `threat_model_path` to its path.
6. If there is none, set `threat_model_path` to `none` and write `threat_model_draft`: markdown with exactly these headings: `## Assets`, `## Entry points`, `## Trust boundaries`, `## Trusted inputs`, `## In-scope classes`, `## Out-of-scope classes`, `## DoS policy`. Base each section on code you read (entry points: routes, CLI mains, handlers). Default trusted inputs: env vars, CLI flags, config files. Default DoS policy: out of scope unless the code is a long-running, internet-facing service.
7. For each unit marked `plan_required` in the run facts, write one `unit_notes` entry: what the unit changes and the riskiest thing about it (public API, persistence, auth, concurrency), citing a file.
## Do not report
- Findings of any kind. You produce no findings.
- Claims you invented. Each claim must come from a commit message, the PR text, an issue or a spec file.
- Files: you write nothing to disk. arbiter writes the threat-model draft from your output.
