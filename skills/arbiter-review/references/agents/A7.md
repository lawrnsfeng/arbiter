# A7 performance
## Mission
Find performance regressions the added code introduces on a hot path, each with a benchmark that would show it.
## Axes
`performance` only (research-axes.md §2a axis 8). LLMs show near-zero recall on perf bugs, so perf findings require E8 (research-decompose-verify.md §3a, S4).
## Read these language references
`idioms.md` rows Performance; `cookbook.md` rows Benchmark (appended below).
## Checklist
1. N+1: a query, request, file read or other I/O call inside a loop over a collection that a single batched call could serve.
2. Quadratic work: nested loops, `in`/`includes`/`contains` on a list inside a loop, repeated string concatenation in a loop, sorting inside a loop.
3. Allocation in hot loops: building a new list, map, regex or buffer on each iteration when one could be reused.
4. Sync I/O or CPU-heavy work on an async path or event loop.
5. Missing pagination or limit on a query that can return an unbounded set.
6. **Hot path required.** Show the code is on a path that runs often or on large inputs: a request handler, a loop over user data, a caller in a loop. Cite it. Give the growth (e.g. "one query per item; n = items per page, up to 100").
7. The commit messages may say the change is a perf change; check that claim too.
## Do not report
- Micro-optimisations without a stated n and a hot path.
- Code that runs once at start-up or in tests.
- Asymptotic worries with no benchmark idea.
- Lines this change did not add.
## Proof plan hints
- E8 is mandatory: a benchmark A/B on base vs head (`cookbook.md` Benchmark row: pytest-benchmark compare, `go test -bench -count=10` + benchstat, criterion baseline). Give the input size in `idea`.
- A query-count assertion in a test supports the claim but the gate still needs E8.
